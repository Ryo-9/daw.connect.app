# Security Policy

## 目的

初心者 2 人が GPT/Codex を使って開発するときに、秘密情報、ユーザーデータ、GitHub、外部サービスを最低限安全に扱うための方針です。分からない設定を推測で本番へ適用せず、特に DB、認証、権限、AWS、S3、Stripe、課金は専用タスクと二人のレビューを必須にします。

## 1. アカウントを守る

- GitHub と利用する外部サービスで、それぞれ別の強いパスワードを使う
- パスワードは共有せず、信頼できるパスワードマネージャーを使う
- GitHub、メール、クラウドで MFA（二要素認証）を有効にする
- 二人が同じ管理者アカウントを共有しない
- 不要になった端末、セッション、権限を速やかに解除する
- リカバリーコードはリポジトリや普段のチャットと別の安全な場所に保管する

## 2. GitHub とブランチを守る

- `main` への直接 push を禁止し、ブランチ保護を設定する
- 1 タスク 1 ブランチ 1 PR とし、作成者以外がレビューする
- lint / build / テストを PR の必須確認にすることを検討する
- 強制 push、履歴書き換え、大量削除は原則行わない
- 公開リポジトリでは、すべてのファイルが全世界に見られる前提で扱う
- PR の差分に秘密情報、個人情報、内部 URL がないことを確認する

## 3. 秘密情報をコードに入れない

秘密情報には、API キー、パスワード、アクセストークン、秘密鍵、DB 接続文字列、Webhook secret、署名 URL などが含まれます。

- 秘密情報は環境変数または承認された秘密管理サービスで扱う
- `.env.local` など実値を含むファイルを commit しない
- `.env.example` には変数名と安全なダミー値だけを書く
- ブラウザへ渡る環境変数にサーバー専用の秘密を入れない
- ログ、テストデータ、スクリーンショット、Issue、PR、Codex の依頼文へ秘密を書かない
- 秘密が混入した場合は、ファイルを消すだけで済ませず、直ちにキーを失効・再発行し、履歴と影響を確認する

## 4. Codex / GPT を安全に使う

- 依頼に変更可能範囲、禁止範囲、完了条件を書く
- コマンド、差分、追加パッケージ、外部接続を人が確認する
- 実ユーザーデータ、秘密情報、非公開ファイルをプロンプトへ貼らない
- Codex に本番環境や外部サービスを操作させる前に、対象、変更、費用、戻し方を確認する
- 生成された認証・権限コードは、正常系だけでなく「他人のデータへアクセスできないこと」をレビュー・テストする
- 「動いた」だけで安全と判断しない

## 5. 依存パッケージを増やしすぎない

- 追加前に、本当に必要か、公式・継続保守されているか、ライセンスは問題ないかを確認する
- パッケージ名の入力間違いによる偽物に注意する
- 追加・更新は専用の差分として `package.json` とロックファイルをレビューする
- 依存関係の脆弱性通知を確認し、影響と更新リスクを評価する
- メジャー更新を他の機能変更と同じ PR に混ぜない
- 不明なインストールスクリプトを理解せず実行しない

## 6. 入力と出力を信用しない

- フォーム入力、URL パラメータ、API リクエスト、ファイル名を検証する
- 文字数、形式、範囲、必須項目、許可する値をサーバー側でも確認する
- HTML をそのまま表示せず、XSS を防ぐ安全な表示方法を使う
- SQL 文字列を手作業で連結せず、安全なクエリ機能を使う
- エラー画面や API 応答に内部構成、スタック、秘密、他ユーザー情報を出さない
- 状態を変える操作で CSRF、二重送信、連打、再送を考慮する

## 7. 認証と権限

- 認証方式は実績あるサービス / ライブラリを候補比較して決める
- セッション Cookie は本番で `Secure`、`HttpOnly`、適切な `SameSite` を設定する
- ログイン済みかの確認と、対象バンドを操作できるかの確認を分ける
- `user_id`、`band_id`、ロールなどクライアント送信値を信用しない
- バンド A のメンバーが URL を変えてバンド B のデータを見られないことをテストする
- 招待トークンは推測困難、短期間、一回限りとし、平文保存を避ける
- メンバー削除、退会、バンド解散時のアクセス失効を確認する

## 8. ファイル共有

- 保存先を非公開にし、アクセス権確認後の短時間 URL を使う案を優先する
- 許可する拡張子だけでなく、実際のメディアタイプや内容も検証する
- 1 ファイル、1 ユーザー、1 バンドの容量上限を設ける
- 元のファイル名をストレージキーとして直接使わない
- 悪意あるファイル、巨大ファイル、重複、アップロード未完了への対策を検討する
- 削除、退会、バンド解散時にファイル本体も適切に処理する
- 音源の著作権と共有範囲を利用者へ分かりやすく示す

## 9. 個人情報とデータ

- MVP で収集する情報を必要最小限にする
- 収集目的、利用範囲、保存期間、削除方法を説明する
- 本番データをローカル環境やテストへコピーしない
- テストには架空の名前、メール、音源を使う
- ログと分析データにメール本文、コメント本文、ファイル URL を安易に残さない
- バックアップも本体と同じレベルでアクセス制御し、削除要件を考慮する

## 10. ログ、監視、バックアップ

- エラー調査に必要な最小限の情報と追跡 ID を記録する
- ログの閲覧権限と保持期間を決める
- 認証失敗、権限拒否、異常なアップロード、費用急増を監視対象にする
- バックアップは取得だけでなく、復旧できることを定期的に確認する
- 監視サービスへ送るデータにも秘密情報や個人情報を含めない

## 11. インシデント対応

漏えい、誤公開、不正アクセス、費用急増などが疑われた場合:

1. 影響を広げる操作を止め、二人へ連絡する
2. 関係するキー、セッション、権限を失効する
3. 対象の環境、期間、データ、操作ログを保全・確認する
4. 必要ならサービスやアップロードを一時停止する
5. 影響を受ける利用者と外部サービスへの連絡要否を判断する
6. 原因、対応、再発防止を秘密情報を除いて記録する

証拠となるログを慌てて削除せず、秘密値そのものは共有しません。

## PR ごとの最低確認

- [ ] タスク外の変更が混ざっていない
- [ ] 秘密情報、個人情報、実データが含まれていない
- [ ] 新しい入力に検証と安全なエラー表示がある
- [ ] 非公開データの認証・権限確認がある
- [ ] 依存追加の理由と安全性を確認した
- [ ] `npm run lint` と `npm run build` が通る
- [ ] 必要なテスト、とくに権限拒否のテストが通る
- [ ] 失敗時、削除時、取り消し時の動作を確認した
- [ ] 未対応事項とリスクを PR に記載した
